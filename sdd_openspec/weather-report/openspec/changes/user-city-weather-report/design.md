## Context / 背景与现状

当前天气功能假设“城市”由外部上下文或固定配置给定，用户无法主动切换或选择城市；这限制了跨城市生活场景（常驻 A 城、出差 B 城）、多城市对比查看、以及用户对特定地点的长期关注。  
本设计基于 `proposal.md` 中的目标，增加一套“城市搜索 + 选择 + 天气展示”的能力，并在不破坏现有天气查询能力的前提下，扩展前端 UI 与天气 API 查询方式；同时，在天气报告界面中增加一个 3D 地球可视化视图，用于展示用户当前选中城市的大致地理位置。

约束与前提假设：
- 前端为 Web / 桌面浏览器环境，允许使用本地存储（如 `localStorage`）缓存最近一次选择的城市。
- 已存在基础天气查询能力（例如根据城市 ID 或经纬度查询天气），本次主要在“按城市名搜索 + 绑定城市 ID”上扩展。
- 后端或第三方天气 API 可能存在调用频率限制，需要在交互和缓存层面避免无效的频繁调用。

## Goals / Non-Goals 目标与非目标

**Goals / 目标：**
- 支持用户在前端界面中通过城市名称搜索，并从结果列表中明确选择一个城市。
- 在选择城市后展示结构化的天气报告，包括：当前温度、天气描述（如多云、小雨）、以及可选的短期预报摘要。
- 记住用户最近一次选择的城市，使其在再次访问时自动加载该城市天气，减少重复搜索操作。
- 统一前端在“城市搜索失败、网络异常、API 错误”等情况下的错误展示样式和文案。
- 在天气页面中提供一个可交互的 3D 地球视图，并在地球上以明显标记展示用户当前选中的城市位置。

**Non-Goals / 非目标：**
- 不在本次设计中覆盖复杂的多城市对比（例如同屏对比多个城市的图表等），仅支持“一次选择一个城市”的查看模式。
- 不在本次设计中引入完整的账户体系或云端同步收藏城市列表，城市偏好先只保存在本地。
- 不对天气 API 的具体供应商做重构或大幅抽象，仅在调用接口与数据模型上做必要适配。
- 不构建完整的 GIS / 地理信息平台，仅提供与天气功能相关的基础 3D 地球展示能力（旋转、缩放、单点标记）。

## Decisions / 关键设计决策

1. **城市实体模型**  
   - 采用统一的 `City` 结构体（或 TypeScript 接口），包含至少：`id`（唯一标识）、`name`（展示名称）、`country`（国家/地区）、可选 `lat` / `lon`。  
   - 前端的城市选择组件只依赖此统一结构，避免直接耦合底层天气 API 的返回结构。

2. **搜索与选择交互模式**  
   - 使用“输入框 + 下拉候选列表”的模式：用户输入城市名，触发节流后的搜索请求，候选列表展示城市名称 + 国家信息。  
   - 用户必须从候选列表中显式点击（或键盘选中）某一项，才视为选中城市，避免纯自由文本导致无法绑定城市 ID。

3. **本地持久化策略**  
   - 在成功选择城市后，将 `City` 精简信息序列化为 JSON 存入 `localStorage`（如键名 `lastSelectedCity`）。  
   - 页面初始化时，优先尝试读取该值并恢复为默认城市；若不存在或解析失败，则回退到现有默认行为。

4. **天气数据获取与缓存**  
   - 城市一旦选定，通过城市 ID（或经纬度）调用现有天气查询接口获取天气数据。  
   - 在同一次会话中，如果用户重复选择同一城市，可复用最近一次成功返回的数据（简单内存缓存），减少 API 调用次数。

5. **错误与空状态处理**  
   - 将“城市搜索无结果”“网络错误”“API 返回错误码”等情况进行统一归类，前端以友好文案 + 可重试按钮的形式提示。  
   - 所有错误均不会导致页面白屏，而是以模块内“空状态面板”方式展示。

6. **3D 地球可视化实现方案**  
   - 在前端采用浏览器端 3D 渲染能力（如 WebGL），基于轻量级 3D 引擎或封装组件实现地球球体渲染与基础交互（旋转、缩放）。  
   - 通过城市的经纬度（若 API 支持）或近似坐标，在地球表面绘制一个明显的城市标记（如高亮点或图钉），并在用户切换城市时更新标记位置与视角。  
   - 3D 视图作为天气报告页面中的一个附加可视化模块存在，不阻塞核心天气数据的加载与展示；在性能较差设备上可退化为简单的 2D 地图或关闭 3D 渲染。

## Risks / Trade-offs 风险与取舍

- **风险：搜索请求过于频繁 → 触发 API 限流**  
  - 取舍：在前端加入输入节流（例如 300–500ms）与最小输入长度（如至少 2 字符），避免无意义请求。
- **风险：城市命名歧义（同名城市过多）→ 用户难以选中正确城市**  
  - 取舍：在候选列表中展示国家（以及可用时展示省/州），并允许用户通过继续输入细化搜索。
- **风险：本地存储数据被清理或格式变更 → 无法恢复上次选择城市**  
  - 取舍：在解析失败时安全回退到默认城市行为，不影响核心功能；必要时在版本升级中做向后兼容处理。
- **风险：不同天气 API 的数据结构不一致 → 前端处理复杂度上升**  
  - 取舍：在数据访问层做一次统一的适配，前端只依赖统一的天气数据模型。

- **风险：3D 渲染性能与兼容性问题 → 影响页面流畅度**  
  - 取舍：为 3D 视图增加启用/禁用条件判断（如设备能力检测或用户开关），在不支持或性能不足时自动降级为静态图或完全隐藏 3D 视图。
